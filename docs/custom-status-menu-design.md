# VS Code 自定义状态栏工具菜单设计

## 1. 背景与目标

为 VS Code 扩展 `vscode-tools` 增加一个状态栏入口，用于集中运行工作区脚本和 VS Code 命令。用户可以维护自己的菜单项，不需要每次打开集成终端手动输入脚本路径，也不需要在命令面板中反复搜索常用命令。

首版目标：

- 在 VS Code 底部状态栏显示一个稳定入口。
- 点击入口后打开底部 Panel 中的自定义工具视图。
- 支持新增、编辑、删除自定义项。
- 支持在集成终端运行工作区内的 PowerShell 脚本，以及执行 VS Code 命令 ID。
- 使用 VS Code 原生交互控件完成首版管理流程，不引入第三方依赖。

首版暂不支持：任意 Shell 脚本、命令参数编辑、菜单分组与排序、脚本运行历史、远程/虚拟文件系统中的脚本执行、导入导出。

## 2. 交互方案

### 2.1 状态栏入口

扩展激活后创建一个 `StatusBarItem`，设置清晰的文本、Tooltip 和点击命令。点击入口后打开扩展贡献的底部 Panel 容器，并聚焦其中的 WebviewView：

1. 面板标题与“管理工具”入口。
2. 按保存顺序排列的自定义工具列表；点击名称运行，尾部管理按钮进入该项的原生管理操作。
3. 列表为空时显示“添加工具”入口。

工具列表由 WebviewView 展示，页面只发送菜单项 ID 和固定动作类型，实际运行仍由扩展宿主根据工作区存储解析目标。状态栏不承载多个按钮，以免占用状态栏空间。

### 2.2 管理流程

点击面板管理入口后，打开原生 Quick Pick 管理列表。列表包含“新增工具...”和已有工具；选择已有工具后可选择编辑、运行或删除，删除前要求确认。

新增和编辑使用 `showInputBox`、`showQuickPick` 组成分步表单：

1. 输入菜单名称，不能为空，去除首尾空白。
2. 选择类型：`工作区 PowerShell 脚本` 或 `VS Code 命令`。
3. 脚本类型通过 `showOpenDialog` 选择 `.ps1` 文件；命令类型输入 VS Code 命令 ID。
4. 校验字段后保存完整菜单项。

编辑类型时重新按目标类型显示相应字段，并清理另一类型的专属字段。取消任一步骤均不保存部分数据。首版阻止忽略大小写后的同名项，并给出明确提示。

底部工具列表使用 WebviewView，以满足从状态栏直接进入列表的需求；新增、编辑字段仍使用 VS Code 原生输入控件，避免重复实现表单验证。若后续需要批量编辑、拖拽排序或更丰富的表单，再扩展 Webview 消息协议和管理页面。

## 3. 菜单项数据

建议首版通过扩展的 `context.workspaceState` 保存，工具项随当前工作区隔离，避免脚本相对路径在不同仓库间意外指向错误文件。使用带版本号的存储键，例如 `vscodeTools.customMenuItems.v1`。

建议的数据结构：

```ts
interface CustomMenuItem {
  id: string;
  name: string;
  type: 'script' | 'command';
  script?: {
    workspaceFolderUri: string;
    relativePath: string;
  };
  commandId?: string;
}
```

约束：

- `id` 使用稳定的随机 ID；编辑时不改变 ID。
- `name` 为菜单显示名称。
- `script` 与 `commandId` 按 `type` 二选一，保存前校验，不保存无效组合。
- `workspaceFolderUri` 标识多根工作区中的脚本所属根目录；`relativePath` 使用相对于该根目录的路径。
- 读取存储时校验版本与数据结构。遇到损坏或不兼容数据时，保留原值并提示用户，不静默覆盖。
- `workspaceState` 对无工作区窗口没有可用的工作区存储；无工作区时仍可显示状态栏入口和命令类操作，但新增工作区脚本应提示先打开文件夹或工作区。

若未来增加可跨工作区复用的全局命令项，可将全局命令和工作区脚本拆分存储；首版不因此增加双层配置模型。

## 4. 执行规则

### 4.1 工作区脚本

- 首版只接受本地 `file:` 工作区中的 `.ps1` 文件，因为集成终端需要可传给本机 Shell 的文件路径。
- 文件选择器以选中的工作区文件夹为范围；保存前校验文件确实位于所选工作区根目录内，并确认文件存在、扩展名为 `.ps1`。
- 多根工作区要让用户选择或明确显示脚本所属的根目录，不根据当前活动编辑器猜测归属。
- 执行前重新解析并验证工作区根目录和脚本路径，处理文件被移动、删除、工作区根目录失效等情况。
- 使用 `vscode.window.createTerminal` 创建或复用专用终端，在终端中发送经过 PowerShell 单引号转义的脚本调用命令；不要把用户输入拼入未转义的命令片段。复用终端前应使用稳定名称标识本扩展创建的终端。
- `sendText` 只负责把命令发送到终端，不代表脚本执行成功。首版通过终端展示输出和错误，不显示“已成功完成”的误导性提示。

### 4.2 VS Code 命令

- 保存 VS Code 命令 ID，例如 `workbench.action.reloadWindow`，而不是命令面板显示的本地化标题“Developer: Reload Window”。命令面板标题会受语言和版本影响，不能作为稳定执行标识。
- 用户在表单中输入命令 ID。保存时检查非空；可使用 `vscode.commands.getCommands()` 做存在性提示，但执行前仍要处理命令不存在或目标扩展未激活的情况。
- 运行时调用 `vscode.commands.executeCommand(commandId)`，将异常转换为可读错误提示。
- 首版不支持命令参数。执行用户配置的命令会触发对应 VS Code 命令的实际行为，管理界面应清楚显示命令 ID，并在删除时确认。

## 5. 推荐模块边界

建议按职责分开，避免把 UI、持久化和执行逻辑都堆在扩展入口：

- `src/extension.ts`：注册状态栏入口及命令，管理生命周期。
- `src/menu/menu-item.ts`：菜单项类型与基础校验。
- `src/menu/menu-store.ts`：读取、写入和迁移工作区状态。
- `src/menu/menu-provider.ts`：处理原生工具项管理流程。
- `src/menu/menu-view-provider.ts`：提供底部 Panel WebviewView 并校验页面消息。
- `src/menu/menu-executor.ts`：根据类型执行脚本或 VS Code 命令。

文件名是建议，不是首轮实现的硬性要求；如果项目采用不同结构，应以现有项目结构为准。VS Code API 仅从扩展宿主代码调用，纯数据校验尽量保持为可单测的逻辑。

## 6. 错误处理与安全边界

- 用户取消文件选择或输入时正常返回，不报错、不写入半成品。
- 脚本路径失效、越出工作区、文件类型不支持或终端创建失败时，显示具体原因，并提供回到编辑该项的入口。
- 命令 ID 不存在或执行抛错时显示命令 ID 和简明错误；不得让扩展异常导致宿主崩溃。
- 对路径做路径段级别的根目录包含校验，不能只用字符串前缀判断（例如 `repo-other` 可能以 `repo` 开头）。
- 不接受用户直接输入任意终端命令；脚本目标由工作区文件选择器提供，并在执行时再次验证。这不能消除仓库脚本本身的风险，运行前用户仍应信任并检查脚本内容。
- 终端发送文本可能依赖当前默认 Shell。首版明确支持 PowerShell `.ps1`；若要支持 Bash、CMD 或其他 Shell，应分别实现可靠的参数转义和执行策略，不复用 PowerShell 拼接逻辑。

## 7. 验收标准

1. 扩展激活后状态栏入口可见；点击后打开并聚焦底部 Panel 工具视图。
2. 空列表显示添加入口；单项和多项均显示名称与执行目标，运行和管理按钮分别工作。
3. 可以新增、编辑和删除脚本项与命令项；取消流程不产生部分保存；重载窗口后配置仍存在。
4. 单根与多根工作区均能选择正确脚本，路径含空格和单引号时仍能正确发送给 PowerShell。
5. 无工作区、非本地工作区、文件移动或删除、无效命令 ID、终端创建失败均有可理解的反馈。
6. 运行 `workbench.action.reloadWindow` 可执行窗口重载；文档及界面使用命令 ID，而非依赖命令面板本地化标题。
7. 不新增第三方依赖；扩展编译和相关自动化测试通过。

## 8. 实施顺序建议

1. 注册底部 Panel 容器与 WebviewView，接通状态栏入口。
2. 实现带校验的菜单项模型、工作区存储和页面消息校验。
3. 实现工具列表交互，并沿用新增、编辑、删除的原生管理流程。
4. 实现命令执行与 PowerShell 脚本执行，并覆盖路径转义和失效路径。
5. 增加单元测试与扩展宿主测试，按验收标准验证多根工作区和异常分支。

实现说明：项目已实现底部 Panel WebviewView 工具列表；新增、编辑和删除字段沿用 Quick Pick/InputBox 原生管理交互。
